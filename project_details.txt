1. Problem statement and proposed solution
Zakat and charitable giving in Pakistan runs almost entirely on trust. You donate, maybe you get a receipt or a 
generic "thank you" post, and that's usually where it ends — you never really know if your specific contribution 
reached anyone. I looked at how other platforms have tried to fix this, like BitGive's GiveTrack, which uses 
blockchain to make the movement of money traceable. That's useful, but it only solves half the problem — it proves
the money moved, not that the delivery actually happened the way it was reported. A photo can be reused from an 
old distribution, a location can be faked, and most social apps strip GPS metadata automatically anyway, so even 
"proof" photos often can't be checked at all. That's the real gap TrustTrack is built for: not recording donations,
which everyone already does, but verifying whether the evidence NGOs upload is genuine, and whether an NGO's 
track record over time actually holds up. This matters most for small and mid-size NGOs handling Zakat, who don't 
have the resources for blockchain infrastructure or manual audits but still need a credible way to show donors their 
money was used honestly.

2. Detailed project description

Every donation on TrustTrack gets a unique tracking ID the moment it's made. When the NGO delivers the aid, they 
upload proof against that ID — a photo, GPS location, and timestamp. Where it gets interesting is what happens after 
the upload. I run an Error Level Analysis pass on the image, which looks at JPEG compression artifacts — if part of
a photo was edited or spliced in, that region compresses differently than the rest, and ELA picks that up even 
when it's invisible to the eye. Alongside that, I check the photo against every previously submitted image using 
perceptual hashing, so if an NGO tries to reuse the same photo across two different tracking IDs, the system catches 
it even though the image itself hasn't been "tampered with" in the traditional sense — it's just recycled, which ELA 
alone would never flag. Then there's a metadata check comparing the photo's EXIF GPS and timestamp, when present,
against what the NGO claims. I'm treating missing EXIF as "lower confidence" rather than an automatic fail, because 
I found out most phones strip that data on their own during upload, so punishing its absence would unfairly flag 
honest NGOs. A content check confirms the photo actually matches the claimed aid type, so a food-parcel photo can't
get passed off as a medical delivery. Individual deliveries that fail any check aren't silently rejected, they get 
flagged for the NGO to explain or re-upload, because this is meant to support human review, not replace it. On top
of the per-delivery checks, I roll every NGO's verification results into an organization-level trust score, so donors 
aren't just seeing "was this one photo real" but "does this NGO have a consistent track record of genuine, non-duplicated 
deliveries over time" — which is closer to how trust actually works in practice. Donors can also ask their own donation
history questions in plain language, like where their Zakat went this year, and get answers pulled only from their actual
verified records, so the system can't make things up about real money.

3. Technical approach and technologies

For image authenticity I use Error Level Analysis — recompressing the uploaded image at a known JPEG quality and 
comparing it to the original to expose inconsistent compression regions. I picked this over training a full deep 
forgery-detection model because it's CPU-only, doesn't need a large labeled dataset, and is well-documented in digital 
forensics research, which made it realistic to actually finish inside the build window rather than half-building something 
heavier. To catch reused photos, I added perceptual hashing (the imagehash library) — every new upload gets hashed and 
compared against prior submissions, and near-identical hashes get flagged as likely reused, which is a fraud pattern 
the ELA check alone can't see since a recycled photo isn't technically tampered. For metadata, I pull EXIF GPS and 
DateTimeOriginal tags and cross-check them against the NGO's declared delivery details, again treating gaps as a confidence 
signal rather than a hard fail. For matching the photo to the declared aid type, I'm using a lightweight vision-language model 
through an open API or the Qoder free tier instead of training something from scratch, since zero-shot classification is good
nough here and doesn't burn my limited build time. The NGO trust score is just a rolling aggregation of verification pass
rates and duplicate flags over each organization's delivery history, stored and queried from the same database, so 
it didn't need a separate model. The donor Q&A assistant is retrieval-augmented — donation records stored in a vector
database (pgvector on Postgres, so I'm not adding a separate service to manage), retrieved per donor, and answered by a
n LLM restricted to only cite what it retrieved. Backend is Postgres with a Node/FastAPI layer, frontend in React. I 
deliberately skipped blockchain, since that solves fund-movement trust, which platforms like GiveTrack already handle 
well, and isn't the problem I'm actually solving here.
